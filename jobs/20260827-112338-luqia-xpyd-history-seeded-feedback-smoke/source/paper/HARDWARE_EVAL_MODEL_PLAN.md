# Model work gating the L40S+L4 hardware evaluation

Scope: we are dropping simulation and evaluating SWEEP-LLM (and baselines) on the
real L40S+L4 cluster. The predictive models are **kept** — they are the scheduler's
online decision engine — but their *outcomes* are now measured on hardware, not
generated by the models. The tasks below are **calibration + validation**, not a
full retrain, unless a validated assumption fails.

Prereqs already done:
- KV per-token cost set to the measured **59 µs/token** (`schedulers/common.py`).
- Feasibility described honestly as a utilization envelope (`models_rewrite.tex`).
- Deployed models verified as the fixed monotonic-HistGBM stack (`artifacts/paper/models/`).

## P0 — required before / during the hardware run

### 1. SLO-conditioned utilization envelope `rho_max(g, phase, TP, f, SLO)`
Replaces the fixed `rho <= 1` gate; makes the scheduler genuinely SLO-aware.
- **Derive (no new hardware):** `calibrate_rho_envelope.py` reads the existing
  `Phase2_Results_{L4,L40S}/master_results.csv` and, in the scheduler's own rho
  units, emits the largest rho at which measured P99 still meets each SLO.
- **Wire into the gate:** in `sweep.py` `_predict_class_metrics`, replace
  `rho_pf > 1.0 or rho_dc > 1.0` with `rho_pf > rho_max_pf(...) or rho_dc > rho_max_dc(...)`,
  loading `rho_envelope.csv`. Keep `guard_k < 1` (e.g. 0.9) as a safety margin.
- **Validate on hardware:** at each SLO, measure realized P99 for the configs the
  scheduler admits. **Target: false-safe (admitted but violates) ≈ 0**; report it.
- **Decision:** if the envelope is non-monotone in rho (safe at high rho, unsafe at
  low rho for some shape), switch `--per-shape` on and gate per short/long bucket.
- **CAVEAT found while calibrating (blocks the decode side):** for DECODE, the SLO
  signal `p99_tpot` does NOT detect overload — at high IL (8192), high rate (50),
  ol=1024 the model predicts rho≈116 (L40S) / 634 (L4) while measured p99_tpot stays
  ~70–115 ms (SLO-met). TPOT is per-token inter-arrival *within* a request; under decode
  overload the queue backs up (TTFT/goodput suffer) but TPOT stays flat, so the
  monotone-safe frontier admits absurd rho. **Fix the decode envelope against sustained
  decode throughput / goodput (offered vs served tokens), not p99_tpot.** Prefill (gated
  on p99_ttft) is fine — its envelope is sane (rho_max ≈ 0.07–1.6, SLO-sensitive).
  Median decode rho is ~2 and 63–65% of profiled points read rho>1, which also says the
  decode *capacity* scale needs a hardware re-anchor (C_dc^ref, see capacity_ref).
- **RESOLVED on existing data** (`calibrate_decode_capacity.py`, no new hardware):
  rebuilt decode capacity on a GOODPUT/stability signal — `r_served = achieved_dc_tps /
  (rate*OL) >= kappa (0.95)` — folding TPOT into a single SLO-conditioned safe capacity:
  `C_dc_SLO(c,s) = max over (stable AND p99_tpot<=s) of achieved decode tok/s`.
  Re-normalizing `rho_dc = offered / C_dc_stable` collapses the scale from median~2 /
  max 116–634 to **median 1.02 (L40S) / 1.04 (L4)** — interpretable utilization again;
  the old "rho=116 but TPOT fine" points are exactly the saturated ones (r_served≈0.04),
  now correctly rho>1. Finding: **69% (L4) / 56% (L40S) of profiled points were hidden
  decode overload that p99_tpot never revealed.** Artifact: `artifacts/paper/models/
  decode_capacity.csv` (per gpu,il,ol,tp,freq,slo → C_dc_SLO_tps, C_dc_stable_tps,
  confirmed flag). Coverage: L40S 176/280 configs have a capacity (52 with a confirmed
  saturation knee); L4 156/261 (71 confirmed). The ~40% without a confirmed knee (single
  high-rate point, or saturates at lowest tested rate) need a conservative fallback:
  borrow a lower-freq/TP bound, do NOT extrapolate upward.
- **Runtime gate becomes** `rho_dc = D_dc / (eta * C_dc_SLO(c,s)) <= 1`, D_dc=rate*OL,
  eta≈0.85 margin — clean and interpretable, no giant rho_max correction. TPOT model is
  KEPT (folded into the capacity label; still available as a diagnostic/sentinel).

### 2. Proxy assumptions `prefill_proxy_ol = decode_proxy_il = 32` — RESOLVED (query fix, no refit)
The code predicted prefill from IL only and decode from OL only.
- **Ablation on existing data** (`analyze_proxy_assumptions.py`): both proxies FAIL the
  10% bar. Decode TPOT vs IL at fixed OL: median spread 172% (L4) / 291% (L40S), >10%
  in 86–94% of groups, rising with IL in 81–91% (KV-cache-size effect). Prefill TTFT vs
  OL: median 43–45%, >10% in 79–82%. Both proxies invalid.
- **Fix was a QUERY change, not a refit:** `DECODE_REG_FEATURES` already carry `log_il`
  and `log_kv_pressure`; `PREFILL_REG_FEATURES` carry `log_ol`. The models were trained
  on the full `(IL, OL)` — the scheduler was just discarding it by substituting 32 at
  inference. `sweep.py` now feeds the real (weighted-mean / per-class) IL **and** OL to
  every phase prediction (`_build_phase_loads` tracks both dims; all 5 call sites +
  `_estimate_reference_capacities` updated). Config knobs `prefill_proxy_ol` /
  `decode_proxy_il` are now dead in the live scheduler.
- **Still validate on hardware** (2-factor sweep as originally planned) to confirm the
  trained models extrapolate correctly across the full `(IL, OL)` grid on real hardware.

### 3. KV-transfer model `T_KV = alpha_route + beta * N_tokens + T_reshape(TP_pf, TP_dc)`
The current `tau_kv * IL` misses fixed overhead and TP-layout cost; 8192×59µs ≈ 483 ms
is SLO-binding, so this matters under the SLO-conditioned envelope.
- **Experiment:** cross-node KV handoff microbench + end-to-end TTFT delta, sweeping
  prompt length, `TP_source × TP_dest`, and concurrent-transfer count. Record exactly
  what is measured (serialization? reshape? overlap with decode? one-way vs ack?).
- **Decision:** fit `alpha, beta, T_reshape`; if `T_reshape` (TP mismatch) is large,
  the scheduler should prefer matched-TP cross-pool routes.

### 4. Hardware-oracle regret experiment (the headline defense)
Directly answers "is this just model-driven self-validation?"
- **Procedure:** on a batch of representative windows, exhaustively **measure on
  hardware** every (route, bundle, TP, freq) in a controlled small space; take the
  measured lowest-energy feasible config as the **hardware oracle**. Then run
  SWEEP-LLM and report, per window:
  - feasible-selection accuracy (did it pick a truly-feasible config?),
  - energy regret `(E_selected - E_oracle) / E_oracle`,
  - config-match rate, search-space coverage, decision latency.
- **Claim it supports:** *even a lightweight, deployment-specific model selects
  near-oracle low-energy configs on real hardware, at low false-safe rate* — much
  stronger than "our simulation is accurate."

### 5. Wording (paper) — already partly done; finish
- "optimal config" → "predicted-best feasible over the enumerated candidate set"
  (design already says the search is not globally exhaustive; confirm no residual
  "optimal" claims after the hardware rewrite).
- Remove the sim-derived throughput-saturation numbers from §eval_models (their
  source dir was deleted); re-derive on hardware only if the gate is actually wired in.
- **Drop the false prefill/decode symmetry.** The data disproved "prefill classifier
  looks at TTFT, decode classifier looks at TPOT." Correct narrative: *Prefill
  feasibility is bounded primarily by the TTFT frontier. Decode feasibility requires
  BOTH a stability condition (sustained decode-token goodput) AND a service-quality
  condition (TPOT), because decode overload accumulates in the admission queue without
  materially degrading the inter-token latency of requests already being served.*
  New model structure (asymmetric): (1) prefill safe-capacity (stability + TTFT);
  (2) decode stable-capacity (sustained decode-token goodput); (3) decode SLO (TPOT,
  or fused into SLO-conditioned capacity — the deployed choice); (4) power (energy
  ranking); (5) KV handoff (route latency).

## P1 — strengthens the model; some need new profiling

### 6. Mixture-shape features (vs weighted-mean IL/OL)
Two mixtures with the same mean IL can have very different tail behavior.
- **Add features:** p50/p90/p99 of IL and OL, short/medium/long class fractions,
  length variance, max class length; or keep the **class-level demand vector**
  `D_pf = (D_pf,1..K)` instead of collapsing to a mean.
- **Profile:** a few dozen representative *mixed* workloads (unimodal, bimodal, few
  very-long prompts, few very-long generations, class-mix shift). Refit if the mean
  collapses tail risk.

### 7. Pool-level multi-instance power & capacity composition
Code uses `P_pool = n_inst * P_per_instance` and `rate / n_inst` (perfect balance).
- **Validate:** for several full pool configs, compare predicted vs **measured whole-pool
  power**, and run with the **real router** to expose replica imbalance / short-window
  burstiness (a 2 req/s class over 4 replicas is not 4×0.5 req/s steady streams).
- **Decision:** if per-instance linear power over/under-predicts, add a pool-level
  correction; if imbalance dominates P99, feed per-replica arrival variance to the model.
